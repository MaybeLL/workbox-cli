# 基于仓库上下文协作设计

从目标仓库根目录的 `AGENTS.md` 找到长期上下文，默认路径为 `docs/Vision.md`、`docs/Decisions.md` 和 `docs/Implementation.md`。分别用它们核对目标、已确认的约束和当前行为。用源码或测试核实能查明的事实，把用户的时间留给需要判断的取舍。

## 建稿与续聊

纯探索先在对话里进行。用户明确进入需求设计时，查找 `docs/TD/` 里对应的方案。首次使用[同目录模板](TD-template.md)建立 `docs/TD/<需求主题>.md`，状态为「讨论中」。同一需求从讨论到交付后沿用同一文件。续聊先读原稿，核对引用的决策是否仍然有效，简述已定事项，从下一个待定问题继续。决策依据改变时，只重议受影响的部分。

## 一次解决一个取舍

1. 已有 Decision 足以回答时，引用编号和它对本方案的具体影响，直接沿用。
2. 遇到未覆盖的场景或拟改变决策时，一次只问一项，等用户答复。列出真正可行的选项，各自说明关联的决策编号、是否需要打破原约定、用户会看到什么结果，再给出推荐与理由。没有直接依据就说明这是新取舍。
3. 每确认一项，立即写回 TD。本次实现选择留在方案里。若未来其他需求也应遵守，向用户展示原约定、拟写入 Decisions 的具体条文、理由及影响。方向获认可而条文未定时，保留为待定；具体改法已明确确认后，同步更新 Decisions 和影响表。撤销决策时保留编号、原因和替代决定（如有）。

## 成稿、审阅与批准

用模板将状态置顶，在目标与现状之后列出 Decision 影响表，逐项标明沿用、新增、修改或撤销。模块职责变化时写清调用者、输入、对外行为、内部承担的复杂性和失败结果。默认用 Mermaid 表达关系、时序或状态，按问题选图；写出起始条件、动作和可观察结果，按需补充失败、重试或兼容场景。

新增、修改或撤销 Decision 的 TD 默认请独立 Agent 审阅**完整稿**；全部沿用时自行复核，用户指定时也独立审阅。检查决策有无遗漏、图与验收是否一致、建议是否被误写成定论。将新出现的实质取舍带回用户逐项讨论。

影响行为、长期约束或验收的事项尚未解决时维持「讨论中」。关键取舍已定、完成相应审阅后，将整稿标为「待确认」并提交用户。单项确认或审阅通过均不足以批准整稿。只有用户明确确认整份最终稿才能写「可交付开发」；该状态仅记录方案审批。实质变更退回「讨论中」，修改完成后重新确认整稿；修错字或链接保留原状态。维护长期上下文时，先与维护者确认具体改动。愿景与决策在确认后更新。实现导览在对应变更完成、经过审阅和验证后更新。
