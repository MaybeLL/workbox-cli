# Workbox 设计决策

以下编号用于开发讨论和变更审查，调整决策时保留编号。每条记录描述已确认的产品方向；当前版本的行为见[使用说明](../README.md)。这些取舍所服务的用户场景见[产品愿景](Vision.md)。第二阶段关于文档、Skill 和 GitLab 访问的条目是开发依据，已落地的流程见[实现导览](Implementation.md)。

## D-001 配置与实例

**决定**　团队成员可以共同维护一份或多份面向不同场景的 Workbox 配置，每个需求创建一个本地工作目录作为实例。对外统一使用“Workbox 配置”和“Workbox 实例”。配置命令为 `workbox workbox-config`，实例命令为 `workbox plan`、`workbox create` 和 `workbox status`。

**理由**　同事可以共享仓库知识和工作方法，每个需求又有独立的分析上下文。

**约束**　从分析进入开发时沿用需求目录，并支持沿用当前 Agent 会话。实例使用创建时取得的配置快照，之后编辑共享配置只影响后续创建的实例。

## D-002 创建时的团队上下文

**决定**　每份 Workbox 配置显式选择仓库、文档和 Skill。团队决定约定写什么、选哪些 Skill、怎样使用它们。实例提供仓库清单，并落地团队选中的内容。

**理由**　团队知道哪些仓库与自己的工作有关，这些仓库可能分属不同 GitLab Group。

**约束**　配置必须能显式选择跨 Group 的仓库。Agent 在尚未检出业务源码时就能取得仓库地址并找到团队工作指引。团队归属用于组织仓库，实际访问权限由代码托管服务判定。

## D-003 按需获取代码

**决定**　让 Agent 可以通过远程搜索和读取源码开始分析，同时保留本地克隆能力。

**理由**　影响分析可能涉及许多仓库，实际需要本地验证或修改的往往只有其中几个。

**约束**　`workbox plan/create` 默认不克隆业务仓库，也不提前解析业务仓库的分析基线。`plan` 本地检查配置与路径；`create` 可以获取配置选中的文档和 Skill。Agent 按用户指令决定何时检出哪些仓库，检出位置沿用各仓库的 `target_dir`。远程分析证据不足时，说明缺口并询问用户。

## D-004 分析范围与基线

**决定**　由全局 Workbox Skill 指导 Agent 按用户指令确定本次分析的仓库和版本，允许在同一次跨仓搜索中为不同仓库指定不同版本。

**理由**　同一团队配置可能用于分析默认分支，也可能用于核查某次发布，选择取决于当前需求。

**约束**　用户已明确的范围和版本直接采用。对仍不明确的部分，在首次跨仓检索前一次确认。用户随后调整指令时，按最新指令更新相应仓库的范围或版本，并复核受影响的结论。例如，支付仓查 `release/11`，其他仓查已确认的默认分支；本次选择只对当前任务生效。

## D-005 开发隔离

**决定**　每个实际需要修改的仓库使用自己的原生 Git worktree。

**理由**　同一需求可能横跨多个仓库，隔离变更可以保留分析时使用的基线。

**约束**　用户要求为某仓库创建开发 worktree 时，该指令涵盖准备其缺少的本地基线。开发 worktree 位于需求目录的 `.workbox/worktree/` 下，修改落在对应的 worktree 中。已有基线检出的工作文件和 HEAD 保持原样，只读仓库可以继续远程查阅。

## D-006 团队 Skill 的归属与安装

**决定**　用户或团队在来源处维护 Skill 内容。Workbox 保存注册信息，团队配置按需引用，创建实例时将选中的 Skill 安装到实例目录。

**理由**　同一个 Skill 可在多个配置中复用，作者也可以沿用已有的发布方式。

**约束**　Skill 按名称注册一次，多份 Workbox 配置可以引用。注册只登记来源，创建实例时才安装到项目级 `.agents/skills/`，供支持该目录的 Agent 发现。没有选中用户 Skill 时不创建该目录。首版来源和命名规则见 D-010。

## D-007 需求目录创建与初始化脚本

**决定**　CLI 准备目录，并将本次配置快照中的初始化脚本交给 Agent 或用户审阅和执行。

**理由**　同一份配置可能被多位同事复用。脚本需要哪些本地仓库、会产生哪些文件，取决于团队的工作流。

**约束**　创建目录不会自动执行配置中的初始化脚本。若任务需要运行脚本，使用此次创建返回的正文，在已有授权范围内执行，并检查约定产物后再报告初始化完成。

## D-008 官方 Skill 的作用域

**决定**　官方 `workbox` Skill 通过 `workbox skill install` 安装在用户全局，Workbox 实例只安装团队选中的 Skill。`workbox` 是官方保留名，团队以 Git 或 npx 注册同名 Skill 时，CLI 直接提示名称已保留。

**理由**　Agent 在创建实例之前就需要知道怎样维护配置，在实例内也需要同一套远程分析和按需检出指引。

**约束**　全局 Skill 指导 Agent 理解用户意图并调用相应 CLI。例如用户说“帮我注册 `npx skills add https://github.com/mattpocock/skills --skill grill-me`”，Agent 从原命令提取来源和名称，调用 Workbox 完成注册。关联 Workbox 和安装到实例分别发生在用户选择该项和创建实例时。

## D-009 团队 Markdown 的来源与版本

**决定**　根 `AGENTS.md` 和配套 Markdown 采用同一机制。团队直接在 Workbox 配置中逐项填写 GitLab 文件来源、分支或 commit，以及实例内的相对落地路径。首版仅支持 GitLab 来源，无需单独注册文档。

**理由**　团队在 GitLab 维护原文，可以自由组织入口和相对链接。例如根文件引用 `docs/review.md`，只要把评审约定配置到这个路径，链接就能在实例内使用。

**约束**　只取清单中明确列出的文件，原样写入，不递归抓取链接。团队未配置根 `AGENTS.md` 时不生成该文件；配置后也不追加官方指引或 Skill 索引。同一次创建中，同一仓库、同一分支只解析一次 SHA，相关文档统一按该 SHA 读取。下一次创建重新解析分支，配置为 commit 的文件始终按指定 SHA 读取。

## D-010 用户 Skill 的注册来源与名称

**决定**　注册名取自 Skill 本身，用户无需另填名称。

| 首版来源 | 注册时如何确定名称 | 创建实例时使用的来源 |
| --- | --- | --- |
| GitLab 或 GitHub 仓库 | 读取指定位置的 `SKILL.md`，使用其中的 `name`。缺少名称则注册失败。 | 子目录省略时取仓库根目录；版本省略时跟随默认分支，也可指定分支或 commit。安装所选 Skill 及其配套文件。 |
| `npx skills add <来源> --skill <名称>` | 直接使用 `--skill` 指定的名称。 | 仅支持此种 npx 安装形式，按登记的来源和名称执行项目级安装。 |

**约束**　同名同来源重复注册返回“已注册”。同名不同来源报告冲突并保留原配置，只有显式更新才会改来源。Git 来源后来声明了不同名称时，创建实例应指出登记名和实际名并报告失败。删除仍被引用的注册项时，列出引用它的 Workbox 配置；解除全部引用后才可删除。从一份配置解除引用不影响其他配置或已创建的实例。

## D-011 实例落地路径与创建成功条件

**决定**　保存 Workbox 配置时检查路径冲突；创建时把选中的文档和 Skill 全部准备好，才发布到用户指定的目标目录。

**理由**　文档可以共用父目录。提前占用某个仓库的检出位置，或只装好部分团队上下文，都会让后续任务遇到难以追溯的问题。

**约束**　文档之间不得同路径或出现文件与子路径冲突；文档路径不得与仓库 `target_dir`、`.workbox/` 或 `.agents/skills/` 重叠。保存时指出相冲突的项和路径。创建时在临时位置准备内容；任一必需项失败，报告具体项和原因，用户指定的目标目录保持未创建，修复后可用原命令、原路径重试。此成功条件涵盖配置项就绪，后续初始化脚本仍按 D-007 交接。

## D-012 GitLab 身份与远程代码访问

**决定**　`workbox init` 可按 GitLab 实例配置用户自己的 token，也可跳过并在需要时补配。Workbox 直接调用 GitLab API，同一实例的文档下载、代码搜索和源码读取共用本机为该实例配置的凭据。

**理由**　同事可以共享 Workbox 配置，各自以本人权限访问代码。Agent 可调用 Workbox 完成读操作，无需安装 `glab` 或取得 token。

**仓库身份**　Workbox 用 GitLab 实例和完整项目路径（含子组）识别仓库。指向同一项目的 HTTPS、SSH 和 SCP 风格地址共享这份身份。远程分析走该实例的 HTTPS API，本地检出沿用团队登记的 Git 地址。常见的同主机地址自动归一；SSH 与 API 使用不同主机名或存在歧义时，用户在本机 GitLab 连接中为实例登记一次 SSH 别名，供该实例下的仓库复用。补配后可在原需求目录重试，共享仓库配置和实例快照保持原样。

**约束**　token 按实例保存在个人环境，排除在共享配置与导出包之外。搜索和读代码限定在当前 Workbox 的仓库清单内。按已确认的仓库与版本逐仓检索，处理分页并报告命中与实际覆盖范围；按 commit SHA 和路径读取源码以核对证据。某仓不可访问、检索未完成或后端不支持指定版本时，明确标为未覆盖，不静默切换默认分支或将失败记为零命中。

## D-013 配置导入导出与 Skill 注册

**决定**　导出 Workbox 配置时，包内同时携带所引用 Skill 的注册信息。导入时在当前配置库登记这些 Skill 并恢复引用，创建实例时才安装。

**验收**　一位成员用一条命令导出配置文件，另一位成员用一条命令导入到新配置库。导入后的 Workbox 具有相同的仓库选择、目标路径和版本提示、初始化脚本、文档来源与版本及落地路径、所选 Skill 及其注册来源，无需手动补录。个人 GitLab token 仍按 D-012 单独配置。

**理由**　使用独立 SQLite 的同事可以通过导入取得完整配置，使用共享 MySQL 的同事可以复用已有登记。

**约束**　导入时，同名同来源直接复用；同名不同来源报告冲突，整次导入保留目标库原配置。

**Skill 来源校验**　导入时只检查注册信息的完整性、配置引用和名称冲突，不联网访问 Skill 来源，也不要求本机已安装 `npx`。创建选用该 Skill 的 Workbox 时，再验证来源并安装；失败按 D-011 处理。

## D-014 深模块与旧逻辑清理

**决定**　从调用方要完成的操作设计接口，把必须一起执行的步骤和失败恢复放在同一个模块内。接口说明输入、结果及失败后留下的状态。

**理由**　例如，创建方只需知道实例是否已发布、失败项是什么、能否用原路径重试。暂存位置、取消和发布顺序由创建模块统一处理。

**约束**　用调用方实际使用的入口验证成功与失败。引入抽象前检查它能隐藏哪些复杂性，合并只做转调的层。替换流程时同步清理废弃分支和失效断言；核对生产调用、脚本、旧数据和兼容测试，保留仍有使用契约的命令别名、包格式、迁移路径和有效保护。

## D-015 方案审批与重新确认

**决定**　每份 TD 分别记录单项取舍的确认情况和整份方案的状态。只有用户明确确认整份最终稿，方案才能标为「可交付开发」。

**理由**　同意一个选项只解决当前问题。接手者需要知道哪些取舍已定，以及哪一版完整方案已获批准。

**约束**　Agent 最多推进到「待确认」。拟新增、修改或撤销长期 Decision 的方案，提交用户确认前默认由独立 Agent 审阅。已批准的方案若改变用户可见行为、长期约束或验收标准，退回「讨论中」，仅重议受影响的部分，再由用户确认整份新稿。修正错字、链接等编辑性改动保留原状态。
