# Workbox

Use the installed `workbox`. Check its version and `--help` for syntax. Use `--format json`; inspect the exit code, error, and any partial data. Use the user's instance and installed CLI capabilities. If a needed command is missing, explain which CLI upgrade is needed.

## Set up this machine

- For “import this here”, first use the configured store. On `NOT_INITIALIZED` with no backend preference, run `workbox init --backend sqlite --skip-skill --format json` and continue. An explicit shared store/MySQL choice takes precedence. Use private credential files; report setup or connection errors against the selected store. A deliberate backend switch can use `--copy-config` or `--no-copy-config` according to the user's intent.
- Configure or rotate personal GitLab credentials with `auth gitlab set --host HOST --token-file FILE`. Keep tokens on the user's machine. For differing SSH and API hosts use `auth gitlab alias set --ssh-host SSH_HOST --host HOST`.
- Install or upgrade the official global Skill with `skill install` (optional `--path SKILLS_PARENT`). The CLI verifies the entire previous tree against its receipt. For an unverifiable or modified installation, show the conflict and ask how to handle the existing files. If the CLI reports published files and a failed receipt, repair the reported record problem and retry with the returned arguments. Use a fresh Agent session after an upgrade. To preview CLI removal use `uninstall --dry-run`; execute `uninstall` only for a requested removal. After partial init inspect settings publication before retrying Skill installation.

## Manage team configuration

Use list/show to identify existing items. Use add/update/remove on the appropriate catalog:

- `team-config` holds immutable team keys and editable display labels. Use `repo-config list --team KEY` to find repositories; `repo-config add-team/remove-team` changes one association. `--teams` replaces the full set. Team membership describes ownership. Use GitLab credentials for access.
- `repo-config` holds a URL, default branch and optional summary. `workbox-config` selects repositories with a relative target_dir and optional branch/commit ref, explicit GitLab documents, an optional init script and selected Skills.
- For a change to a Workbox configuration, run `workbox-config show NAME` and pass its opaque revision with `--revision REV` on update, add-skill and remove-skill. For a repository/document addition preserve the existing ordered list, append only the requested item and send the complete array through `--repos-file` or `--docs-file`. Already identical: skip. Explain any occupied destination and ask whether to replace or use another path. For an explicit source/version edit, change only that item. Verify the result. On a stale revision, reread, reapply the original intent and retry compatible changes; ask only about actual conflicts.
- Document entries specify project_url, source_path, target_path and a typed ref. Fetch only selected files; include AGENTS.md when explicitly configured. For repositories an omitted ref inherits the default branch. Preserve the configured checkout path.
- Translate “register npx skills add URL --skill NAME” into `skill-config add --installer npx-skills URL --skill NAME`. For Git use `skill-config add --git-url URL` with optional subdirectory and branch/commit. Use the returned name. Registration records a source; `workbox-config add-skill CONFIG NAME --revision REV` selects it, and instance creation installs it. Remove a selection with `workbox workbox-config remove-skill CONFIG NAME --revision REV`; remove the registration with `skill-config remove NAME`. Infer the intended scope from context, otherwise ask. Report remaining references before removing a registration.
- `config export --output FILE` exports the entire catalog, including unused Skill registrations. If the request names just one Workbox, explain the actual scope and wait for confirmation. For `config import --input FILE`, identical items are reused; conflicts abort the batch. Compare local show results with the package and present concrete differences before modifying either side. After the user chooses each conflict, keep the source file intact. Prepare the final package with those choices. First import any missing dependencies using self-contained temporary packages in dependency order (teams, repositories and registered Skills, then Workbox selections). Include referenced existing entries with their current local definitions in dependency packages. Apply authorized updates to conflicting entries in the same dependency order, using a fresh revision for each Workbox change. Import the final package and read back the result. When all choices adopt incoming content, the original file is the final package. Report completed and pending steps separately if a later operation fails.

## Create and analyze an instance

- Use `plan --config NAME --path DIR` for an explicit preview. For creation run `create` directly with the chosen config and path. Use the requested parent, then team conventions; ask if neither provides it. Choose an unused task-derived child name if omitted. Report the full created path. On preparation failure inspect the item and stage, fix the cause, then retry the original destination.
- To list registered Workbox instances run `workbox list --format json`. Report the recorded path and its current status. A moved or missing directory keeps its record. On request to forget a record use `workbox forget --path DIR` with the listed path; leave the directory on disk. A missing registered target requires forget before reuse. Choose a target outside existing instances.
- If create returns `prepared` with `registration.state: failed`, report the reason and continue at `workspace_path`. The directory is ready; repeating create would hit the occupied target.
- Start with the team's instructions and .workbox/repos.json. For “also look at this repo this time”, run `add-repo --path DIR --url URL` or select a registered name with `--repo NAME`. A URL needs no catalog registration. Resolve ambiguous names with the user. Continue in the same instance without cloning. Update shared configuration separately only when explicitly requested for future instances.
- For `search --path DIR --query TERM`, explicit scope and versions take precedence; otherwise use the whole instance list, each repo's ref hint, then its default branch. Repeat `--repo NAME` and `--ref NAME=REF` as needed. Ask about unmappable intent such as an unspecified production version. Report actual coverage by repository and ref, including partial/error results. Use `read --path DIR --repo NAME --file PATH [--ref REF] [--lines START-END]` to verify a file and cite its commit. Fixed SHA supports file reads; branch search cannot prove exhaustive coverage at a SHA. Check out only when requested.
- Answer a quick lookup in chat. Save impact assessments and handoffs by default; an explicit save/chat-only instruction wins. Write to the user-specified path, otherwise create `.workbox/artifacts/` on first write. Record repo, file and actual read SHA in conclusions. Update the same assessment with the current conclusion first; briefly explain material scope, baseline or judgment changes. Create a separate snapshot only if requested. Keep the manifest ref as configured.
- `status --path DIR` reports actual local checkouts/worktrees. For initialization scripts, or moving from analysis to development, follow the [handoff and worktree guide](references/agent-guide.md).
